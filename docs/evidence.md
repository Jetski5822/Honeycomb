# Evidence

What has been tested for this architecture, how, and what came out. The tests were throwaway programs and are not kept; each result states its setup (package versions, model, number of runs) so it can be re-created. Telemetry-specific results are in the table under "Verified by running" in [telemetry.md](telemetry.md); everything else is below.

Rules for this file: a result is only listed if it was run. A claim that was read from source, or is untested, goes in "Not tested". Re-run the relevant row when a package version changes.

## Setup common to all results

- .NET 10, `Microsoft.Agents.AI` 1.26.0, `Microsoft.Extensions.AI` 10.11.0, `ModelContextProtocol` 2.3.0, `OpenTelemetry` 1.20.1.
- Local model: `docker.io/ai/qwen2.5:7B-Q4_0` through Docker Model Runner (`http://localhost:12434/engines/v1`), with `Microsoft.Extensions.AI.OpenAI`.
- Windows 11 for everything; Linux (Amazon Linux 2023 container, kernel 6.6) where stated.
- Models were scripted fakes unless a row says it called the local model.

## Results in detail

First round, on this machine:

- Docker Model Runner is running, and `http://localhost:12434/engines/v1/models` returns an OpenAI-style model list.
- In `Microsoft.Extensions.DependencyInjection`, a scope created through `IServiceScopeFactory` from within another scope does not share the parent's scoped instances and is not disposed with it.
- In a throwaway test program (`Microsoft.Agents.AI` 1.26.0, `Microsoft.Extensions.AI` 10.11.0, a scripted fake model):
  - An executor can build a `Workflow` and run it with `InProcessExecution.RunAsync` inside its own handler. The inner workflow ran and returned its output, and the outer run took one in-memory checkpoint. The inner workflow's telemetry nests under the outer one, if each workflow enables it.
  - An inner run given its own file checkpoint store, and parked on a human request, was restored by fresh objects over the same directory (4 of 4 runs): the request was raised again with the same id, and the answer completed the run. State survived only when written to a shared scope, not an executor's default scope. The outer workflow's checkpoint holds nothing of the inner run, so the hive would have to keep the inner checkpoint ids itself. A second `FileSystemJsonCheckpointStore` over the same directory in one process fails until the first is disposed. The earlier hang when resuming the outer workflow is explained under "A hang in MAF" below.
  - 20 agents with the same `Id`, run concurrently outside a MAF workflow, did not interfere: each had its own session history and response, and spans had distinct ids. The hosting session store and `ChatHistoryMemoryProvider` were tested in the third round below.
  - `OpenTelemetryAgent` records token usage on the `invoke_agent` span, as the total across the cell's model calls, and `chat` spans carry per-call values. The agent wrapper also double-counts the `gen_ai.client.token.usage` and `gen_ai.client.operation.duration` metrics (see the telemetry document).
  - Two cells of one type and `Id` cannot be bound in one MAF workflow.
- Also in that program, `Microsoft.Extensions.AI.OpenAI` completed a chat against Docker Model Runner (`docker.io/ai/qwen2.5:7B-Q4_0`), and honoured a JSON schema response format. Over 30 calls in each of two modes (a JSON schema, and instructions only), every reply parsed as the requested type and had a valid status, and 27 of 30 had the expected status. The three misses were one question that the model refused. Median latency was 1.4s. The two modes gave the same results, so this does not show the schema format helping. The sample is small: 10 prompts, one model, one simple result shape.

Second round (2026-10-27):

- **Package feed.** On NuGet every package proposed here has a stable version except `Microsoft.Agents.AI.Mcp`, which is alpha only. Latest stable: `Microsoft.Agents.AI` and its `.Abstractions`, `.Workflows`, `.Anthropic`, `.OpenAI` 1.26.0; `Microsoft.Extensions.AI` and `.OpenAI` 10.11.0; `ModelContextProtocol` 2.3.0; `Anthropic` 13.3.0; `Vogen` 8.0.7 (9.0.0 is beta); `Microsoft.ML.Tokenizers` 2.0.1 (3.0.0 is preview); `TestableIO.System.IO.Abstractions.*` 22.3.0; `xunit.v3.mtp-v2` 4.0.2; `Moq` 4.21.0; `OpenTelemetry` 1.20.1; `dotnet-coverage` 18.12.0.
- **Floating versions.** Central package management rejects a floating version by default (error NU1011). With `<CentralPackageFloatingVersionsEnabled>true</CentralPackageFloatingVersionsEnabled>` in `Directory.Packages.props`, `Version="*"` resolved to the latest stable release and skipped the pre-releases (`Vogen` 8.0.7, not 9.0.0-beta). A build still depends on the day it restores.
- **The hive skeleton.** Planning cells as `AIAgent`s, cells created in child DI scopes with a scoped `ICellContext` and matched from `IEnumerable<ICell>` by type (no factory), the three re-spin counters on a `FakeTimeProvider`, `Vogen` value objects, a checkpoint snapshot, and a resume in a fresh container: 33 checks pass. Details are in the "Verified by running" table in telemetry.md. The rules for resuming in the tech stack document (only the checkpointed cell runs again; answered and unanswered cells keep their saved result; superseded re-spin attempts are skipped) worked as written, after one correction: the skeleton first re-ran unanswered cells and superseded attempts, and had to skip them.
- **Cancellation.** A cell must return a `cancelled` result and not let `OperationCanceledException` escape, otherwise MAF's `OpenTelemetryAgent` marks its span as an error.
- **Checkpoint file replacement on Windows.** The "write a temporary file, then move it over the snapshot" step failed with `UnauthorizedAccessException` in 80 of 80 attempts when two saves ran 0 ms apart in a new directory, and in 0 of 160 when they were 50 ms or more apart. The destination is briefly locked after it is written, most likely by antivirus or an indexer. A retry with a short back-off (20 ms) cleared it every time (one retry each). Saves must be serialised, and the move must be retried. A corrupt snapshot and a leftover half-written temporary file were both handled correctly.
- **Anthropic.** MAF's adapter completed a chat against a fake Anthropic server on localhost, with the key header and model in the request, provider `anthropic` on the span and the usage mapped. MAF's `AsAIAgent` helper gives a random agent id, so the hive builds its own `ChatClientAgent` over the SDK's `IChatClient` (see the telemetry document).
- **Compaction.** With a trigger of 8 messages, a sliding window held the history at 7 messages and truncation at 8, where with no compaction it grew by two every turn.
- **Tokenizer.** `Microsoft.ML.Tokenizers` with the `o200k` vocabulary counted 212, 968 and 2,732 tokens for three test prompts, against 232, 1,050 and 3,019 reported by the local `qwen2.5` model. It under-counts by about 8 to 10%, so it is an estimate and not the model's own count.
- **MCP.** An MCP server's tool bound to a cell and ran, as `execute_tool echo`. The SDK emits its own spans (source `Experimental.ModelContextProtocol`, for example `tools/call echo` with kind `Server`) and the trace context reached the server.
- **What the local server enforces in a JSON schema.** Docker Model Runner enforces the structure (required fields, `const`, `enum`, types), and ignores the bounds (`maxItems`, `maxLength`, `maximum`). It returned `"green"` for an enum that excluded the colour the prompt asked for, and returned three items for `maxItems: 1`. A `[MaxLength(3)]` attribute does produce `maxItems` in the generated schema, but the server returned 4 or 5 items regardless. So status values should be enums in the schema, and every limit must be validated in code with the bounded re-ask, as this draft says. **Corrected in the seventh round:** the server does enforce `maxItems` and `maxLength`. The `Microsoft.Extensions.AI` OpenAI adapter rewrote the schema before sending it, moving each bound out of the schema and into the field's description as prose, so the server never saw it. The claim above that the server ignores bounds is withdrawn. Validating every limit in code is still the rule.
- **Reliability with a larger schema and longer contexts.** 72 calls (two modes, three context sizes up to about 3,000 tokens, answerable and unanswerable tickets): all parsed, all had the expected status, and every piece of evidence quoted was found in the ticket. 11 of 18 answerable replies in each mode broke the "at most 3 findings" limit, which is the bound that never reached the server (see the seventh round). Median latency was 2.7 to 4.7 s when nothing was found and 10 to 11 s when findings were listed. The schema mode and the instructions-only mode gave the same results.
- **`dotnet-coverage`.** `dotnet-coverage collect "<command>" -f xml -o cov.xml` produced Visual Studio coverage XML (`results`, `modules`, `functions`, `ranges`, `source_files`) from a run, which is the format the Sonar setting reads.
- **A hang in MAF.** `InProcessExecution.ResumeAsync` on a checkpoint with nothing pending never returns. With a token it returns when the token is cancelled, with no error. With no token it waits forever.

Third round (2026-10-27):

- **Sharing an `Id` in MAF's session store.** `InMemoryAgentSessionStore` keys a session by the agent's `Id` plus the `AgentSessionStoreKey`. A second agent instance with the same `Id` and the same key was given the first one's history, so two cells of one type would share a conversation. A different `Id` was isolated. A key with a `cell` partition (`new AgentSessionStoreKey(conversation, { ["cell"] = cellId })`) isolated same-`Id` cells: 20 concurrent cells saved and read back with no mixing, and a fresh instance with the same cell key got its own history back. The session holds history only; the new instance's own instructions were used. `AIHostAgent` over the same `Id` shares in the same way. The rule for the hive: if a session store is ever used, key it by the durable cell id, never by the agent `Id` alone. The hive does not use one today.
- **Sharing an `Id` in `ChatHistoryMemoryProvider`.** The provider does not read the agent `Id` at all: it stores and searches by the `ApplicationId`, `AgentId`, `UserId` and `SessionId` the caller puts in its scope. With a search scope of the user only (as in MAF's sample), a different cell type saw the first cell's messages. With user plus agent `Id`, different types were isolated but a second cell of the same type saw the first one's messages. With the cell id as `SessionId` in both scopes, same-type cells were isolated and a fresh instance with the same cell id found its own earlier messages. Recalled memory is injected as a user message, so content capture covers it. The hive does not use the provider; if it does, scope by cell id. `Microsoft.Agents.AI.Hosting` has previews only (1.26.0-preview), and the in-memory vector store comes from `CommunityToolkit.VectorData.InMemory` 1.0.1.
- **Ten kinds of cell, local model** (qwen2.5 7B, JSON schema response format with enums, 6 cases per kind with a clear expected answer, each run 10 times, 530 calls). 527 replies parsed. Right answers: depth judge 60/60, router 60/60, goal folder 40/40 (kept the new fact and the aim, under 700 characters), specialist answered/cannot_answer/checkpointed 60/60 (every checkpoint had a question), classifier 60/60, injection inside a ticket 30/30 (stayed `cannot_answer` with no findings), neighbour tool call 50/50 (right neighbour, and no call when none was needed), reviewer 50/60, planner 47/60, re-spin decider 40/60. Every wrong answer came from the same few cases failing 10 times out of 10, not from random slips, so they are judgement errors under placeholder prompts (one paragraph each, written for the test; no prompt work has been done yet), and say little about what the model can do once the prompts are written: the reviewer flagged a parameterised query as unsafe; the planner gave three independent documents as sequential goals and not parallel ones; the re-spin decider chose `respin` when the cell lacked access to logs and `route_to_other_cell` when the ticket did not exist, though it did obey the "no respins remaining" rule 20/20. The 3 unparseable planner replies started as valid JSON and were cut off; they most likely hit the 600-token output cap, which was not confirmed. Median latency 0.7 to 4.7 s. So structure holds across cell types, and the hive still needs the validation and bounded re-ask for the rare cut-off reply. What this does show is that structure holds without prompt work. Revisit the three weak cells (re-spin, parallel flags, reviewer) once the prompts are written, and rerun `json5` to compare.
- **Linux.** The test program was published self-contained for linux-x64 and run in an Amazon Linux 2023 container (kernel 6.6, WSL2). Replacing a file with a temporary file and a move succeeded 300 of 300 times by every method, and two saves 0 ms apart in a new directory succeeded 40 of 40 with no retry used, on the container's overlay filesystem, on tmpfs and on a bind mount of the Windows disk. The whole hive suite passed there (54 checks, plus 6 Anthropic, 3 compaction, 5 MCP and 13 id-sharing). So the retry is needed on Windows only; keeping it everywhere costs nothing. macOS was not tested.

Fifth round (2026-10-28): the goal body design.

Setup: qwen2.5 7B as above, each case run 10 times, throwaway program, one-paragraph placeholder prompts. Specialist sources were short invented notes (a query review, a performance report, a database operations note for a "fix the slow checkout query" goal; a log analysis, a client review and release notes for a "mobile login failures" goal), each with distractors such as other tables, other services and other numbers. Four runs, which differ in one thing at a time:

| Run | Specialist prompt | Order of fields in the result |
|---|---|---|
| A | First wording | `status` first |
| B | Second wording, written after A failed | `status` first |
| C | Second wording | Contributions first, `status` and `summary` last |
| D | Second wording | As C, and the planning cell's criterion step added to the pipeline |

- **Part 1, does a specialist fill the fields honestly?** Five cases: findings, a source silent on part of the aim, a hedged claim ("I think the cache might be disabled, I have not checked"), an irrelevant source, a source stating an objective. Checks are code: every `quote` is a substring of the source after normalising case and punctuation, every `supports` names a fact in the reply, every fact has evidence, every number in a fact is in the source.
  - **Runs A and B: the fields were not used as designed.** Three cases failed 10 of 10 (findings, silent on part, states a requirement). The model read `confirmed` as "facts that finish the aim", answered `cannot_answer`, left `confirmed`, `evidence` and `proposed_criteria` empty, and put every fact it found into `context` and the rest into `open_questions` (the replies I read were from run A). The second prompt wording did not change the counts.
  - **Runs C and D: putting `status` after the contributions fixed most of it.** Clean replies, of 50 each: A 20, B 18, C 43, D 43 (the hedged claim was 10 of 10 in all four runs and the irrelevant source 10 of 10 in three, with two empty replies in B; silent on part went from 0 to 10 of 10 in C and D). What remained: the findings case, 6 and 5 of 10 (three or four replies still `cannot_answer` or missing the index), and the objective case 7 and 8 of 10. The likely cause is that a model writes `status` before it has written any fact, so it commits to `cannot_answer`. That is a reading of the result, not something checked further.
  - **Honesty.** In C and D, where `confirmed` was filled, no reply was flagged for a quote not in the source, an evidence item pointing at a missing fact, a fact without evidence, or an invented number. The hedged claim was never confirmed (40 of 40 across the four runs). In A and B this is not informative, because `confirmed` was empty.
  - **Empty replies.** In runs B, C and D some calls returned empty text and did not parse: 4 of 50 in B, 3 of 50 in C, 2 of 50 in D, against 3 of 530 in the ten-kind test. The cause was not looked into. The bounded re-ask in the stack covers it, but the rate is higher with this larger schema.
- **Part 2, can the planning cell judge a proposed criterion?** Six cases against the existing criteria, each run 10 times in A to D. A new, measurable, relevant criterion was accepted 38 of 40 (the other two did not parse). A criterion that contradicted an existing one (40 of 40), one outside the aim (rewrite the page in React) (40 of 40) and a vague one ("good and fast") (40 of 40) were never accepted: contradictions and out-of-scope proposals were rejected and the vague one was rejected rather than rewritten. One already covered by an existing criterion was returned as `change` every time, which I counted as right. "The DBA team has given written approval before the pull request is merged" was **changed**, never accepted, in every reply that parsed (25 of 40 parsed); I had expected accept, and it is a judgement call about whether a process step is measurable, which bears on whether the planning cell uses a model or a rule (open decision 3 in the folding draft).
- **Part 3, after folding, does a later cell still get what it needs?** Each run is three specialists reading three sources, a deterministic fold into the body, the planning cell's decision on each proposed criterion (run D), and then a writer cell asked for three facts that come from different sources (for example the table, the columns and the latency target). The same writer is given the folded body with evidence, the body without evidence, and the full transcript (each source and each reply). A run whose specialist reply did not parse is left out.
  - **Run B (second wording, status first).** The model had put the facts in `context`, but the body carries context, so nothing was lost: right 7 of 7 and 10 of 10 for all three modes, and tokens 561 to 642 for the body against 1,303 to 1,352 for the transcript.
  - **Run A (first wording).** The folded body lost facts in some runs, and the writer was right 3 or 4 of 10 and 7 of 10 against 9 of 10 and 10 of 10 for the transcript.
  - **Run C.** Mobile login: 8 of 8 in all three modes, 418 to 550 tokens against 1,392. Checkout: the body was right 2 of 8 against 8 of 8. The latency objective had correctly moved to `proposed_criteria`, which this version of the program never gave to the planning cell, so the later cell never saw it. That is a gap in the program and not the design, and it is why run D added the step.
  - **Run D, the whole pipeline.** Mobile login: no criteria proposed, right 7 of 7 in all modes, 420 to 550 tokens against 1,445. Checkout: 6 complete runs of 10, 6 criteria proposed and 5 taken in, body right 4 or 5 of 6 against 6 of 6 for the transcript, 549 to 613 tokens against 1,523. The misses were the free-text `blocker` (an answer about a performance test or a new index, where the facts held a DBA approval), so the facts reached the body and the writer picked the wrong one. The sample is small.
  - **What this shows.** The body is about half the size of the transcript and, in these runs, loses nothing a later cell needs, when the specialist replies are usable. It does not show a saving for long transcripts: three short notes make a transcript of about 1,300 tokens, so the absolute saving here is small. It does show how a loss would happen: a fact in `proposed_criteria` that the planning cell rejects, or drops by not deciding, is gone from the body.

Nothing here tests a frontier model, nested planners folding upward, or a planner that writes criteria itself.

Sixth round (2026-10-28): compaction inside one cell.
  - **Setup.** A cell with the aim "why did the login endpoint return HTTP 500, and which release introduced the fault", and a scripted history of eight tool calls (about 820 tokens of results by the package's bytes-over-four estimate, 1,378 input tokens as the server counts them with the instructions and schema). The three results that answer the aim come first; five distractors follow. The last turn calls the local 7B model, which returns `confirmed` and `evidence` in the result format. MAF `Compaction` with a trigger of 400 estimated tokens (set low on purpose, to force it), the last three groups preserved, 10 repeats per condition. Each reply is scored for how many of five expected facts appear in the confirmed statements, and for whether each evidence quote is word for word in the tool results as they were first returned, and in the history the model was actually sent.
  - **No compaction.** 3.6 of 5 facts on average (all five in 1 of 10 runs), 46 of 46 quotes verbatim. The baseline is weak: the 7B model often missed the release date or the share of devices.
  - **Sliding window.** The whole history is one turn, so the window kept only the last message: the model saw 1 message and 175 tokens. 0 of 5 facts, 0 of 28 quotes in the tool results, and invented numbers in 4 of 10 runs. It answered anyway.
  - **Truncation.** It dropped the oldest groups, which held the answer. The model saw 9 messages and 716 tokens, recovered 0.1 of 5 facts, and its quotes were verbatim (44 of 52) but about the distractors, so it reported the wrong material with correct quotes. The cause was found in 0 of 10 runs.
  - **Tool result collapse (default).** 1,225 tokens against 1,378, an 11% saving. 3.3 of 5 facts, 54 of 56 quotes verbatim. It keeps the results' text for a recent window and shrinks little here.
  - **Summarising, default prompt.** 1,000 tokens, a 28% saving, 3.5 of 5 facts. Only 9 of 44 quotes were verbatim in the tool results. 29 of 44 were in the summary the model saw, so about 15 of 44 were in neither (reworded).
  - **Summarising, a prompt asking for exact quotes.** 852 tokens, a 38% saving, 3.6 of 5 facts, 6 of 40 quotes verbatim in the tool results, 21 of 40 in the summary. 2 of 10 replies were not parseable.
  - **What this shows.** The facts survive a summary and the verbatim evidence does not. A check that every quote is in the tool results would have rejected about 80% of the quotes after a summarising compaction, whatever the facts were worth. The two cheap strategies fail without any signal: the cell answers confidently from what is left, and in the sliding window case from nothing. Only the strategies that keep the result text verbatim keep the evidence, and they save little, because in a tool-heavy cell the tool results are nearly all of the history.
  - **Limits.** One scenario, 18 messages, a trigger set low to make compaction fire, a scripted history (the model chose none of the calls), the same 7B model as summariser, and a crude fact match on keywords. The "cause found" figures (0 to 5 of 10) show how weak the baseline is and are not compared.
  - **Three ways to keep the evidence, tried on the same cell** (`compaction3`, pooled over six runs of 10 for each condition, so 60 runs; the first five of those used a build in which my fuzzy quote matcher counted repeated words twice, so the fuzzy figures below come from the last run of 10 only). The answer sits at the start of each tool result in this data.
    - **Option 1, notes taken as each result arrives.** After each tool result the model is asked for facts with a quote, and code keeps a note only if its quote is word for word in that result (all 358 notes passed). The notebook is a system message at the head of the history, which compaction does not touch. Every evidence quote the final cell wrote was then verbatim in the tool results: 100% with no compaction, with sliding window and with truncation, 98% after summarising. It also rescued the two strategies that failed before: sliding window went from 0.0 to 3.0 facts of 5, truncation from 0.1 to 2.2. The costs are real. The notes step is 8 extra model calls and about 2,060 input tokens. The notes alone found only 2.9 of 5 facts, so the final cell with notes and no compaction found 2.3 of 5 against 3.4 without notes, and it was sent more tokens (1,889 against 1,378, because the notes repeat what the history holds). With compaction on top it was sent 686 to 1,191 tokens, no fewer than a plain summary (988) except under the sliding window.
    - **Option 2, resolve a reworded quote against the stored results.** In the last run, after summarising, 16 of 39 quotes were accepted by a check that finds the quote's words (80% of them) within a window of the stored results, against 7 of 39 that were verbatim. Sliding window, whose quotes were invented, was accepted for 0 of 33. So the check turned away invented quotes and still turned away 23 of 39 reworded ones. Where the summary kept the wording it did not need the fuzzy check, where it did not it often failed. The fuzzy check also shows only that words resemble the source and not that the quote supports the fact. It is not enough on its own.
    - **Option 3, compaction that keeps the text of the tool results.** Default collapse keeping the last 3 groups: 1,225 tokens (11% less), 3.8 facts, 88% of quotes verbatim. Keeping 1 group: 1,169 tokens (15% less), 3.9 facts, 94% verbatim. Shortening each older result to its first 300 characters: 912 tokens (34% less), 4.9 facts, but 69% of quotes verbatim. First 150 characters: 686 tokens (50% less), 3.4 facts, 62% verbatim. The first 300 characters did best on facts because the answer is at the start of each result in my data and because the distractors were cut. That was an artefact of the data, see the run with the answer at the end below.
    - **The answer at the end of each result** (one run of 10, sentences after the title reversed, checked in what the model was sent). The first-300-characters strategy fell from 4.9 to 2.0 facts of 5 and the first 150 from 3.4 to 1.0, so its earlier result was an artefact of where the answer sat. No compaction found all five facts in 10 of 10 runs (5.0), against 3.4 with the answer at the start, so position alone moved the baseline more than most strategies did. Default collapse keeping 1 group: 5.0 facts, 1,169 tokens (15% less), but 32 of 54 quotes verbatim and 48 of 54 by the fuzzy check. Without any compaction only 53 of 63 quotes were verbatim here (62 of 63 fuzzy), so a quote that is not word for word is not always a compaction loss. Summarising: 3.7 facts, 6 of 10 replies parsed, 3 of 31 quotes verbatim. Notes: 3.0 facts and every quote verbatim (50 to 60 of 50 to 60), with 526 to 1,729 tokens sent. Sliding window and truncation still found 0.0 and 0.2 facts.
    - **What this shows.** Only option 1 kept the evidence rule intact under every strategy, and it cost recall, an extra 2,060 input tokens and 8 calls per cell, and it saved no tokens against a plain summary. Option 3 kept most evidence and saved 11 to 15% with the default formatter, and more only by cutting text, which cost quotes. A summary with option 2's check gave up most evidence. In this test no variant saved more than 15% and kept both recall and verbatim evidence at the level of no compaction, with the answer at the start or at the end of each result.
    - **Limits.** As above, and in addition that 7B notes found 2.9 of 5 facts, so a better model might change option 1 more than the others, and the fuzzy matcher's window and 80% threshold were my choice.

Seventh round (2026-10-30): retests prompted by [industry-research.md](industry-research.md).

Setup: the same model (qwen2.5 7B Q4_0) and server as above, the `validate` modes of `spikes/telemetry-spike` and three small Python scripts that call the server over plain HTTP (kept beside it). Every source, ticket, dispute and payload is **invented**. Counts are small, so read each as a direction and not a rate. No frontier model was used.

- **`maxItems` and `maxLength` are enforced by the server. The earlier finding was a client-library artefact.**
  - Plain HTTP, a list capped at 3 and a prompt that invites many items: 0 of 21 replies went over the cap, against 10 of 10 over (6 items each) with no cap. A hand-written GBNF grammar with `{0,2}` repetition gave exactly 3 items in 10 of 10. The same held for an array of objects, nullable types and `$defs`/`$ref` (0 over in 8 of 8 each, against 7 findings in 8 of 8 with no cap), and `maxLength: 60` held (longest string 60).
  - The exact schema the .NET client generates, sent over HTTP, with six variants (without descriptions, without `$schema`, and so on): 0 of 30 over 3.
  - Through the .NET client, `ChatResponseFormat.ForJsonSchema<T>()` still reproduced the old result: counts of 4, 5, 3 with the cap and without it. A logging proxy between client and server showed why. The adapter **removed `maxItems: 3` from the schema and put it into the field's description** (`"description": "Findings\r\nmaxItems: 3"`), and added `additionalProperties: false`. That transform exists because OpenAI's strict mode rejects those keywords.
  - Passing the schema through the OpenAI SDK's own `ChatResponseFormat.CreateJsonSchemaFormat` in `RawRepresentationFactory` sends it as written: 0 of 8 over 3, against 4 of 8 over with no cap and 2 of 8 over through the library path.
  - Side effect: with a cap and unbounded strings, 7 of 10 replies in the first direct test failed to parse with an unterminated string, which fits the model running on inside the last string until the token limit. I did not check the finish reason in that run. In the second test, with the finish reason recorded, none of 32 replies was cut off, and one shape bounded the strings (`maxLength: 60`). Cap the list and the strings together.
  - Not tested: other keywords the library may also rewrite (`minimum`, `maximum`, `pattern`). The earlier `json4` test of which constraints the server enforces went through the same library path and is not trustworthy until rerun.
- **Asking for contributions, four ways** (`validate format 8`: five cases, 8 repeats, 40 calls per way).

  | Way | Parsed | Clean | Evidence in the source | Evidence shares a word with its fact |
  |---|---|---|---|---|
  | Status first | 39 of 40 | 16 of 40 (40%) | n/a | n/a |
  | Status last | 37 of 40 | **33 of 40 (83%)** | 32 of 32 | 32 of 32 |
  | Two passes (free notes, then status last) | 27 of 40 | 16 of 40 (40%) | 25 of 25 | 25 of 25 |
  | Status last, evidence as a sentence number that code resolves | 40 of 40 | 24 of 40 (60%) | 48 of 48 | 24 of 48 |

  Status last replicates the fifth round (18 and 20 of 50 clean with status first, 43 of 50 with it last). The two alternatives did **not** beat it. Two passes failed to parse in 13 of 40 and was no cleaner. Sentence numbers always resolved to a real sentence, but only half pointed at a sentence that bore on the fact, so the model chose the wrong sentence about as often as it would otherwise have paraphrased. In this test the model **copied quotes word for word in 32 of 32 replies**, on sources of two to four sentences, so the verbatim rule held and the span reference solved nothing. A longer source could behave differently.
- **Concurrency on the local server** (`validate concurrency 3`, the same request at once, up to 400 output tokens each): 1 at once took 14.8 s and gave 27 output tokens/s. 4 at once took 28.5 s and gave 56 tokens/s. 8 at once took 58.3 s and gave 55 tokens/s. Throughput about doubled and then stopped rising, so parallel cells share roughly twice a single cell's speed, and a fan-out of 8 takes about a minute. Windows 11, llama.cpp backend, one run of three rounds.
- **Siblings and implicit decisions** (`validate decisions 20`, temperature 0.8): two isolated cells designed two endpoints of one API, choosing date format, money, id style and field casing. The two designs agreed on all four in **8 of 20** pairs (40%), mostly splitting on money (`integer_minor_units` or `decimal_string`). With a decisions part in each goal, both followed it in 20 of 20. With the sibling's design shown, they agreed in 20 of 20. Enumerated choices only, so the adherence is largely instruction following.
- **Choosing which parts of the goal body a child gets** (`validate partselect 10`, 8 scenarios): the planner gave a child every part it needed in 7 of 8 scenarios, 10 of 10 each, and 0 of 10 on the eighth ("list what is still unknown", which I labelled as needing criteria and open questions, and which arguably needs only the second). It gave 3.8 of 5 parts on average, so it over-includes and saves little. Fixed rules did worse: "criteria and confirmed" covered 2 of 8 scenarios, adding context 5 of 8, and all five parts 8 of 8. The body was small and the needs obvious.
- **A judge settling eight invented disputes** (`validate judge 3`, each shown in both orders, 6 runs per case and condition):
  - Without a code check on the quotes: 30 of 48 right (63%), the same majority in both orders for 6 of 8 cases. Both cases with a missing or false quote failed 0 of 6, because the judge escalated.
  - With a line showing whether code found each quote in its source: 40 of 48 right (83%), order-stable in 7 of 8. The fabricated-quote case went to 6 of 6, "neither claim has a real quote" to 6 of 6, and "three cells with no quote against one with a real quote" to 6 of 6.
  - **In 96 runs the judge never chose the wrong claim.** Every miss was an escalation instead of a verdict, which is the safe direction. Weakest: two true claims answering different halves (2 to 4 of 6 right, escalating instead), and a misread number (3 of 6 with the check).
  - Limits: eight invented cases written by me, mostly with a clear answer, one model. It says nothing about a frontier judge or real disputes.
- **Injection, hand-written payloads, repeated** (`validate injection 5` and `injection2`): eight payloads (plain instruction, authority notice, fake end of source, fake approval, a JSON the model is told to repeat, a mode switch, a task hijack, a polite developer comment), five repeats each, in the ticket text and in a neighbour's `summary` field.
  - First count (the canary string anywhere in the reply): ticket 37 of 40, neighbour 25 of 40. This overcounts, because a cell that quotes the payload as evidence also contains the string.
  - Stricter count (the payload in a content field with no sign it is being described): ticket **24 of 40 obeyed, 9 reported only**, neighbour 3 of 40 obeyed, 11 reported only, and **13 of 40 neighbour replies did not parse**, so that figure is understated.
  - I read the sample replies, and the automatic check errs both ways. Real compliance included `summary: "CANARY-7731 is the ticket number"`, `open_questions: ["open_pr"]`, and a fake "DBA team has granted approval" written into the summary. Some counted as obeyed were the payload copied into `context` without being followed, and some counted as reported were followed ("CANARY-7731 is confirmed as per the new instructions").
  - **Even when the payload is not followed, a cell often copies its text into `context`, and `context` is folded into the goal body for later cells.** Folding carries injected text forward.
  - This contradicts the 30 of 30 result above, which used one simple payload. Payloads were hand-written and not optimised against the model, so a real attacker would likely do better.
- **Error correlation in the ten-kind test** (the third round's saved results): of 43 wrong answers, 40 came from five cases that failed 10 times out of 10, and 3 were unparseable replies. Wrong answers were nearly all deterministic, so asking the same cell again at the same temperature would not change 40 of 43.
